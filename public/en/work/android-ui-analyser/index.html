Closing the Android development loop for AI agents

AUA gives an agent the tools to inspect, control, and verify the Android app it has just changed. Its purpose is to let the agent carry its own work through testing.

01

Close the loop

I built AUA around one question: how can an agent test the Android app it has just changed without handing verification back to a person?

ADB exposes useful commands, but it was not a dependable testing interface for an agent. UI actions failed, app state was difficult to read, and screenshot-driven workflows kept spending calls and tokens to rediscover the same screen.

I kept the repeatable parts of testing function-driven. AUA combines related operations into one call and gives the agent a purpose-built harness and interaction model. The agent decides what to test, while the harness handles mechanics that should be deterministic.

The same harness can control the conditions around the app through proxy tools, network mocking, crash evidence, and guarded database operations. The agent can create the state a test needs, exercise the real app, inspect the result, and choose the next step.

Code→Build→Run→Test→Inspect→Fix↺

The same agent can move from a code change to evidence that the app behaves as intended.

02

The problem

A mobile agent needs two things on every step: a dependable view of the current screen and a safe way to act on it.

The usual screenshot-first loop is expensive and fragile. The agent has to process an image, infer where a control sits, tap raw coordinates, wait, and take another screenshot. As the flow gets longer, the same visual context is processed again and again.

AUA replaces that loop with structured observations and tracked elements. It lets the agent reason about the interface as controls, text, states, and bounds, then act on an element by ID.

03

How it works

01

Read the hierarchy

Inspect accessibility and view data first, returning element IDs, types, text, states, and bounds.

02

Act by element

Resolve the selected ID on the current screen instead of asking the agent to guess a pixel coordinate.

03

Return the result

Wait for the UI to settle and include the next structured observation in the same interaction.

Hierarchy first, vision when needed.

OCR, image detection, and optional visual grounding cover screens whose accessibility data is incomplete. The common path stays lean; heavier perception is a fallback.

04

Beyond a single test

Parallel execution

Automatic device selection and leasing let multiple agents test without competing for the same target.

Reusable knowledge

Flows, screen maps, routes, transitions, and app memory let future agents reuse paths that have already been discovered.

Test the real conditions

Proxy control, network mocking, crash evidence, screenshots, recordings, and guarded database operations give an agent the state and evidence a real test needs.

Agent-ready access

A CLI, MCP server, and plugins for Codex and Claude Code make the same operating model available in different workflows.

05

In use

AUA began as a response to a delivery problem at Luzia and later became open source.

The Luzia Android team uses it to check features after implementation and before release. It can also run agent-driven QA scenarios in parallel. The team’s early testing and feedback shaped the tool, and outside contributors now help develop it.

AUA is public for teams and developers who want mobile agents to work with better UI context and retain what they learn.

Open source

Use AUA or contribute on GitHub.

The repository has installation guides for the CLI, Codex, and Claude Code, along with documentation and the release history.
